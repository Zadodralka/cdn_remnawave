          Yandex Cloud CDN × Remnawave × Xray XHTTP автоматизация

## 🚀 Быстрый запуск (одна команда)

```bash
sudo bash -c "$(curl -fsSL https://raw.githubusercontent.com/Zadodralka/main/setup-yandex-cdn.sh)"
```
---

Скрипт `setup-yandex-cdn.sh` автоматизирует всё, что можно автоматизировать
на стороне сервера, **после того как CDN-ресурс уже создан в консоли
Yandex Cloud** (домен раздачи, источник, SNI, протокол HTTPS к источнику
и т.д.).

## Что делает скрипт

1. **Сам находит** контейнеры nginx и ноды Remnawave (по `docker ps`,
   без необходимости вводить имена руками)
2. **Сам находит** реальный файл конфига nginx — и внутри контейнера
   (через `nginx -T`), и его путь **на хосте** (через `docker inspect`
   mounts) — работает независимо от того, как именно у вас разложены
   файлы (`/opt/remnanode`, `/opt/remnawave` или что-то своё)
3. Выпускает сертификат Let's Encrypt (RSA-ключ, цепочка до
   `ISRG Root X1`, DNS-01 через хук-скрипт, который сам ждёт и проверяет
   распространение TXT-записи по трём резолверам)
4. Разбивает сертификат на `leaf` / `chain` и **пошагово, интерактивно**
   проводит через загрузку в Yandex Certificate Manager (по одному полю
   за раз, с подтверждением на каждом шаге)
5. Правит конфиг nginx **на хосте** (не пытается писать в контейнер,
   если конфиг смонтирован read-only) — с бэкапом до правки, показом
   diff перед применением и автооткатом, если `nginx -t` не проходит
6. Перезапускает контейнер nginx, чтобы подхватить изменения
7. Ставит cron-задачу ежедневной проверки и попытки автопродления
8. Печатает готовые JSON для инбаунда Xray и Host в Remnawave (с уже
   встроенной обфускацией трафика)
9. Прогоняет 8-пунктовую диагностику всей цепочки
10. Идемпотентен — повторные запуски пропускают уже сделанные шаги
11. Между шагами — паузы, чтобы вывод не проскакивал мимо (настраивается)

## Что скрипт НЕ делает (и почему)

- **Не создаёт CDN-ресурс в Yandex Cloud** — это делается один раз руками
  в консоли до запуска скрипта.
- **Не загружает сертификат в Yandex Certificate Manager автоматически**
  — штатного стабильного API/CLI-пути для этого нет (были проблемы с `yc`
  CLI при федеративной авторизации), поэтому скрипт готовит файлы и ведёт
  тебя по шагам вручную (2-3 минуты в консоли).
- **Не добавляет инбаунд/host в Remnawave автоматически** — печатает
  готовые JSON-блоки для копирования в панель.
- **Не включает инбаунд на ноде и не жмёт Restart** — это отдельный,
  легко упускаемый шаг, см. предупреждение ниже.
- **Не может полностью автоматизировать продление без участия человека**
  — DNS-провайдер может не давать API для управления записями.

## ⚠️ САМАЯ ЧАСТАЯ ОШИБКА — не пропусти!

Добавить инбаунд в **Config Profile** — это **не то же самое**, что
включить его на конкретной ноде. После вставки JSON инбаунда:

1. Зайди в **Remnawave → Nodes → твоя нода**
2. Найди список инбаундов у этой ноды и **включи** (тумблер/галочка)
   только что добавленный инбаунд
3. Только потом сделай **Restart Node**

Без этого шага порт никогда не поднимется, сколько ни жди — скрипт
специально останавливается и переспрашивает об этом перед финальной
диагностикой.

---

Скрипт задаст всего три вопроса:
- Домен-источник (origin, где уже есть nginx + сертификат)
- Домен раздачи CDN (тот, что настроен в Yandex Cloud CDN)
- Email для Let's Encrypt

Всё остальное (контейнеры, путь к конфигу nginx на хосте, путь и порт
xhttp-инбаунда, тег инбаунда) — находится/подставляется автоматически.

### Только диагностика (без полной настройки)

```bash
sudo bash setup-yandex-cdn.sh --diagnose-only
```

### Повторный запуск

Идемпотентен:
- Если сертификат уже есть и не истекает в ближайшие 14 дней — выпуск пропускается.
- Если location в nginx уже добавлен — пропускается.
- Если cron-задача уже стоит — не дублируется.
- Старый `config.env` без новых полей — доопределяется автоматически.

## 1. Настройка CDN-ресурса в Yandex Cloud (перед запуском скрипта)

Консоль Yandex Cloud → Cloud CDN → «Создать ресурс»:

| Поле | Значение |
|---|---|
| Тип источника | Собственный сервер |
| Доменное имя источника | `nl.example.com` (ваш origin) |
| Протокол для источников | **HTTPS** |
| Задать SNI вручную | Включить, значение `nl.example.com` |
| Заголовок Host | Своё значение → `nl.example.com` |
| Доменное имя (раздача) | `cdn.example.com` (**отдельный** от origin домен) |
| Кэширование | Выключить всё (TTL=0, gzip выкл, cookie игнор) |
| Перенаправления / CORS / токен / IP-ограничения | Выключить всё |
| Разрешённые методы | GET, HEAD, OPTIONS |

DNS для домена раздачи:
```
CNAME cdn → xxxxxxxxxxxxxxxx.a.yccdn.cloud.yandex.net.
```
(точное значение CNAME-цели покажет Yandex после создания ресурса)

После этого — запускай `setup-yandex-cdn.sh`.

## 2. Профиль Xray в Remnawave

Скрипт печатает готовый JSON и сохраняет его в
`/etc/yandex-cdn-vpn/xray-inbound-<TAG>.json`. Вставь содержимое в:

**Remnawave → Config Profiles → выбрать/создать профиль → Inbounds → добавить**

Ключевые особенности конфига:
- `"security": "none"` — TLS не нужен на уровне Xray, он терминируется в nginx
- `"mode": "packet-up"` — режим xhttp, совместимый с ограничениями Yandex CDN по методам
- Блок `extra` — обфускация: паддинг переезжает из query-параметра в
  заголовок (`xPaddingObfsMode: true` обязателен, без него паддинг
  остаётся в открытом виде как `?x_padding=...` в URL/логах)

**Дальше — см. предупреждение выше про включение инбаунда на ноде.**

---

## 3. Host в Remnawave

Скрипт печатает таблицу настроек и сохраняет Extra-JSON в
`/etc/yandex-cdn-vpn/remnawave-host-extra.json`.

**Remnawave → Nodes/Hosts → Add Host**, поля:

| Поле | Значение |
|---|---|
| Address | домен CDN (например `cdn.example.com`) |
| Port | 443 |
| SNI | тот же домен CDN |
| Host | тот же домен CDN |
| Path | путь инбаунда (например `/yandexpath`) |
| Network | xhttp |
| Mode | packet-up |
| Security | tls |
| **ALPN** | **`h2`** |
| Fingerprint | chrome |
| Extra | содержимое `remnawave-host-extra.json` |

### ⚠️ Почему ALPN обязательно `h2`

Yandex Cloud CDN всегда отвечает клиенту по HTTP/2, независимо от того,
что клиент предлагает через ALPN. Если выставить `http/1.1` — Xray-клиент
получит бинарный HTTP/2-ответ, попытается распарсить его как HTTP/1.1 и
упадёт с ошибкой `malformed HTTP response`.

## 4. Диагностика типовых проблем

| Симптом | Причина | Решение |
|---|---|---|
| Порт 10088 не слушается после Restart Node | Инбаунд добавлен в Config Profile, но не включён на самой ноде | См. предупреждение в начале — включить тумблер инбаунда на ноде отдельно |
| `502` через CDN | Раскатка настроек CDN на edge-нодах ещё не завершена | Подождать 10-60 минут, перепроверить `--diagnose-only` |
| `unable to get local issuer certificate` | Сертификат ещё не раскатился на всех edge-нодах, или цепочка собрана неверно | Проверить `openssl s_client ... Verify return code`, подождать раскатку |
| `malformed HTTP response` у клиента | ALPN выставлен `http/1.1` вместо `h2` | Поправить ALPN на `h2` в Host |
| `device or resource busy` / `Read-only file system` при правке nginx | Конфиг смонтирован в контейнер как read-only bind-mount | Уже исправлено в скрипте — редактируется файл на хосте, контейнер перезапускается |
| Ничего не появляется на экране во время выпуска сертификата | Старая версия скрипта прятала вывод хука в лог-файл | Обновить скрипт; временно смотреть `/var/log/yandex-cdn-vpn/certbot-hook.log` в соседнем окне |
